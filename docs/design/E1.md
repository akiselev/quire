# E1 (headless part): a 100k-line file in the widget

Measured 2026-10-22 by the qe4 builder on master `62de94d` plus the qe4 branch (the fixes below).
The machine is an Intel i7-8750H MacBook (macOS, 12 threads) **shared with other agents' builds**:
load averages were between 7 and 40 during the runs. Absolute numbers are therefore noisy, and
p99 and max suffer most. The numbers below come from a run at load average about 7 to 14, after
a warm-up build.

How to run it: `scripts/cargo.sh bench -p egui_quire --bench e1`. Use `E1_REPORT_ONLY=1` for the
report alone, or `E1_OPEN_ONLY=1` for the open measurement only.

## Setup

- `crates/egui_quire/benches/e1.rs` drives egui headlessly with `Context::run_ui` and synthetic
  `RawInput`. The helper is in `benches/support/rig.rs` and the text generator in
  `benches/support/gen.rs`.
  - The window is 1280×800 at 1 pixel per point, which shows about 53 lines.
  - Wheel scrolling uses `MouseWheel` line events with the pointer over the text, so egui's smooth
    scrolling is included. Typing uses `Text` events plus an Enter after every 14 characters.
- The file is 100,000 Rust-like lines, 3.9 MB in total. Lines vary in length and indentation, and
  about one in nine contains non-ASCII text, so both the monospace fast path and the galley path
  run. There are no tokens and no diagnostics.
- "Editor" is the time inside `CodeEditor::show_in`. "Pass" is the whole `Context::run_ui`.
  Tessellation and rendering are the host's and are not included.
- Allocations are counted with a counting global allocator in the bench binary only
  (`stats_alloc` 0.1, which wraps `System`; our code has no `unsafe`). Per-site attribution was
  done once with `dhat` in a scratch bench that was not committed.
- criterion (`e1_100k/*`) reports mean frame time. The report adds p50, p99 and max over 600
  frames.

criterion, in an earlier run on the same code apart from the fold fix, at lower load: scrolling 3
lines took 451 µs, scrolling a page 1.97 ms, typing 212 µs and an idle frame 125 µs.

- **Scrolling new lines** costs about 45 µs per newly shown line, which is egui's `layout_job`
  (about 50 allocations per line, inside egui). Scrolling 3 lines per frame (180 lines per second)
  is well within the target.
  - A fling of 40 lines per frame (2,400 lines per second) has a mean of 1.8 ms and a p99 of
    4–7 ms.
  - The only way to get that under 2 ms is to shape fewer glyphs per new line, which means
    bypassing `LayoutJob` for plain ASCII lines (proposal P2). That is not a cheap fix.
- **Typing p99** comes from the Enter frames (1 in 15) and from the first character typed on a
  new blank line.
  - Either one changes an indentation level, so the indentation fold ranges are rebuilt from the
    level table: about 0.6 ms when the machine is quiet and up to 1.8 ms under load, at 33k ranges.
  - Ordinary keystrokes cost 0.15 ms.

## Fixes made (internal, no public API)

| Problem found | Before | After |
|---|---|---|
| Typing rescanned the whole document for indentation folds (core3's `Document::fold_ranges` dropped its cache on every edit and the widget asks every frame) | ~100 ms per keystroke at 100k lines | 0.15 ms per keystroke; levels follow `LineEdit`s (`folding::IndentLevels`), and ranges are rebuilt from the u32 level table only when a level or the line count changes |
| `LineWidths::rebuild` looked up each line in the rope | 130 ms on the first frame | one pass over chunks; first frame 13–27 ms |
| `large::check` looked up each line in the rope | 48 ms in `Document::new` | one pass over chunks, 7 ms |
| `count_eols` byte loop | | vectorised LF count when the text has no `\r` |
| `KeyHandling::default()` cloned the keymap on every frame (`CodeEditor::new`) | 63 allocations per frame | `Keymap` shares its bindings in an `Arc` |
| `EditorText::default()` built 14 strings per frame | 14 allocations | one static default |
| Gutter numbers: `painter.text(n.to_string())` on every line | 2–3 allocations per line | numbers go through the galley cache |
| `layout::mono` laid out 256 Ms on every frame | 2 allocations plus layout | cached per font and pixels-per-point, revalidated by a cheap glyph-width and row-height probe |
| `Vec<VisLine>`, `worst_severity_per_line`, line strings split across rope chunks and token runs allocated on every frame | | buffers reused in the editor's memory; no vector when there are no diagnostics |
| `HeightIndex::uniform` rebuilt an O(n) Fenwick tree whenever the line count changed | 0.5–1 ms per Enter | uniform heights are stored as (height, count) and the tree is built only on the first non-uniform `set` |

Clean idle frames went from 254 allocations (20 KB) to 7 (532 B).

The 7 that remain are:
- 2 from ropey's `Chunks` iterator, which allocates its node stack when a visible line straddles
  a rope chunk boundary;
- 1 from `glue::fold_headers`;
- 4 from egui (`Context::interact`, shape lists and similar).

None of them happens per line.

## Follow-ups (not implemented)

Only P1 adds public API and needs approval. P2 and P3 are internal, but each is more than a
cheap fix.

- **P1: `Text::line_into(&self, line: usize, buf: &mut String)`** (or `TextSlice::for_each_chunk`
  without an allocating iterator), in `quire-core`. It would remove the two remaining per-frame
  allocations for lines that straddle rope chunks. ropey's `Rope::chunk_at_byte` walks without
  allocating. The gain is small; I recommend it only if "zero allocations per frame" becomes a
  hard requirement.
- **P2: an ASCII fast path in the line shaper** that builds `Galley` rows directly from cached
  glyph metrics instead of going through `Fonts::layout_job`. This is an internal widget change
  with no public API, but it is a sizeable piece of work and depends on egui 0.37's `Galley`
  internals (`PlacedRow`, `Glyph`), which are public but unstable. It would bring flinging 40
  lines per frame under 2 ms. I recommend deferring it until a wgpu run on real hardware shows
  that the fling matters for the 8.3 ms frame budget.
- **P3: an incremental indentation-fold range update.** Rebuilding only the enclosing ranges
  around an edit would make Enter frames O(edit) instead of O(lines) (0.6–1.8 ms at 100k lines).
  It needs no public API. I recommend it if typing p99 at ≥ 100k lines matters before QE5.

The wgpu part of E1 (p99 frame ≤ 8.3 ms on a GPU machine) is outside this headless bench.
