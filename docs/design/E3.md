# E3: large-file thresholds

Measured 2026-10-22 by the qe4 builder on master `95b2d2c` plus the qe4 branch: the core3 large-file
policy as it is on master, plus the qe4 fixes described in `E1.md`. The machine is an Intel i7-8750H
MacBook **shared with other agents' builds** (load average 7–19 during the runs), so timings are
noisy. The trends are stable across three runs.

How to run it: `scripts/cargo.sh bench -p egui_quire --bench e3`. `E3_ONLY=<substring>` selects
cases.

## Setup

- `crates/egui_quire/benches/e3.rs` uses the same headless rig as E1: the real `CodeEditor` in a
  1280×800 window through `Context::run_ui`.
- Each generated file is run twice:
  - with master's `LargeFilePolicy::default()` (Monaco's thresholds: 20 MB, 300k lines, a line
    over 10k bytes);
  - with the policy off (every threshold at `usize::MAX`), to see what the degraded features cost.
- Measured per case:
  - `Document::new`;
  - open to first frame;
  - net heap after open (a counting allocator; only meaningful for the big files, since the
    small ones show egui freeing earlier galleys);
  - 120 frames of 3-line wheel scrolling from the middle;
  - 120 keystrokes in the middle of the file, or in the middle of the long line;
  - one `actions.find` for a query with many matches, run in core at the document start;
  - 120 keystrokes with that query active.
- Today the policy switches off only what master has. **Indentation folding** is off when the
  file is past the size or line-count threshold.
  - Tokenisation is not wired into the widget yet (the SyntaxDriver is waiting for approval), and
    there is no bracket matching yet.
  - The widget does not yet render a prefix of a long line (`LongLine` is only reported). The
    long-line rows therefore show the cost of rendering the whole line.

## What this says

1. **Size and line count do not threaten frame time** up to at least 39 MB and 600k lines.
   Scrolling stays under 1 ms and typing under 0.5 ms (p99 ≤ 1.5 ms). The widget is virtualised,
   and since qe4 every per-edit structure is incremental: line widths, indentation levels, the
   height index and find.
2. **What does grow with size:**
   - open: about 4 ms per MB plus the first frame;
   - memory: about 1.3 to 2× the file, counting the rope, the saved-text rope (shared until the
     first edit), the line-width table and the indentation levels;
   - **the first find**: about 4 ms per MB, synchronous on the UI thread. The regex runs over a
     joined copy of the text, so a find stalls one frame above about 4 MB and takes 75 ms at
     19 MB and 160 ms at 39 MB.
3. **Folding past the thresholds** costs open time only: 20 ms at 300k lines and 45–90 ms at
   23–39 MB, the one-pass level scan plus the range build. Editing is unaffected, so the degrade
   saves little for core's own features. The thresholds matter for the features not wired yet:
   tree-sitter tokenisation (E5: a full parse of the 20k-line Svelte fixture with all its injection layers takes about 0.6 s, so a 20 MB file would take many seconds even off-thread) and bracket
   pairs.
4. **Long lines are the real cliff.** Editing a line re-lays out the whole line in egui:
   - about 0.35 µs per character, so 3.6 ms at 10k characters, which is fine for "60 fps
     degraded";
   - 40 ms at 100k characters (under 25 fps);
   - about 0.5 s at 1M characters (frozen).

   Scrolling past a long line stays cheap because its galley is cached.

## After widget4: F2 and P2 (2026-10-22)

Measured by the widget4 builder after a warm-up build, at load average 4–5 (before: master
`3eb3f4e`, load 2–3). Treat p99 as an upper bound.

- **F2 is done.** A line with more than `EditorConfig::stop_rendering_line_after` chars (VS Code's
  `editor.stopRenderingLineAfter`, default 10,000; `usize::MAX` renders everything) lays out only
  that prefix, followed by a "…" marker.
  - Only the prefix is copied out of the rope and hashed.
  - A caret or selection end past the prefix is drawn after the marker, and a selection that
    runs past it covers the marker.
  - A click on the marker's right half goes to the line end; inside the prefix it hits the char.
  - Editing, Home/End, find and the a11y runs (the prefix) work on the whole line.
  - Kittests: `tests/wrap.rs` (`long_line_renders_a_prefix…`, `prefix_line_a11y…`,
    `prefix_and_wrap_together`).
  - The prefix setting is separate from `LargeFilePolicy` (as in VS Code), so the "off" policy
    rows below render a prefix too.
- **P2** (the ASCII fast path, `E1.md`) halves the cost of laying out an ASCII line, which shows
  on the 10k-char line, the longest line rendered in full.

| file | before: type mean / p99 | after: type mean / p99 | after: scroll mean / p99 |
|---|---|---|---|
| one 10k-char line | 3.53 / 3.73 ms | 1.54 / 1.72 ms | 0.12 / 0.25 ms |
| one 100k-char line | 38.1 / 42.1 ms | 0.24 / 0.25 ms | 0.13 / 0.27 ms |
| one 1M-char line | 421 / 462 ms | 0.48 / 0.52 ms | 0.14 / 0.28 ms |
| 100k lines × 39 B | 0.24 / 0.33 ms | 0.18 / 0.21 ms | 0.25 / 0.34 ms |

The long-line cliff is gone: typing in a 1M-char line costs 0.5 ms (rope edit, line-width
re-measure, the edited line's find refresh). With a find query active it is 1.4 ms (the plain
query re-searches the edited line, 1M chars). The other rows of the full run are within noise
of the table above, apart from scrolling, which P2 made about 40 % cheaper.

## Recommended thresholds

| Policy field | Recommendation | Why |
|---|---|---|
| `max_bytes` | **keep 20 MB** (Monaco) | Core features are fine well beyond it. Keep Monaco's number for tokenisation and brackets until the SyntaxDriver is wired, then re-measure a full tree-sitter parse of a 20 MB file (E5's bench at 20 MB) and raise it if that stays under about 1 s off-thread. |
| `max_lines` | **keep 300 000** (Monaco) | Same reasoning; 600k lines edit at 0.3 ms. |
| `max_line_len` | **keep 10 000** (Monaco's `stopRenderingLineAfter`); lines longer than `stop_rendering_line_after` (10 000 chars) render a prefix (done, widget4) | Editing a 10k line costs 1.5 ms since P2; 100k and 1M lines cost 0.2–0.5 ms with the prefix. 10 000 keeps E1's 2 ms per frame on long lines. |

Two further findings, both outside the policy struct:

- **F1: the first find should not block the UI thread on large files.** Above about 4 MB, run
  `find_all` as a job on the host's `Spawner`. Until it returns, show "searching…" and keep the
  old (mapped) matches. This needs API (a pending find state, or a find job type), so it is a
  proposal for the coordinator. Since qe4, edits with a plain query active refresh only the
  edited lines and are already cheap. Regex queries still re-search everything on each edit;
  they could get the same treatment when the regex cannot match `\n`, via `regex-syntax`'s
  `Hir` properties (internal, no API).
- **F2: render a prefix for long lines.** Done in widget4 (above).
