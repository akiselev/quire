# E5 / O8: highlighter engine, grammar ABI, re-highlight cost

Decided 2026-10-22 by the quire-syntax builder (QE2), with the measurements below. The machine
was an Intel i7-8750H (macOS) shared with other agents' builds (load average about 3.5–6), so the
absolute numbers are noisy. Their ratios are stable.

## Decision

**Our own query runner over tree-sitter's `QueryCursor`** (`crates/quire-syntax/src/{tree,highlight}.rs`),
not `tree-house` 0.4.

**Grammar change:** Svelte uses **`tree-sitter-htmlx-svelte` 0.1.16** instead of
`tree-sitter-svelte-ng` 1.0.2. Because of that, quire uses **tree-sitter 0.26.13** instead of 0.27.
The other grammars are `tree-sitter-typescript` 0.23.2 (TS and TSX), `tree-sitter-javascript`
0.25.0 and `tree-sitter-css` 0.25.0.

## Grammar ABI (the "[unverified]" in ARCH-QUIRE §3.6)

Every grammar loads through `tree-sitter-language`'s `LanguageFn`, as checked by
`tests/abi.rs`. tree-sitter 0.26 and 0.27 both accept ABI versions 13–15.

| Grammar | ABI |
|---|---|
| tree-sitter-svelte-ng 1.0.2 | 14 |
| tree-sitter-htmlx-svelte 0.1.16 | 14 |
| tree-sitter-typescript 0.23.2 (both dialects) | 14 |
| tree-sitter-javascript 0.25.0 | 15 |
| tree-sitter-css 0.25.0 | 15 |

The ABI therefore fits tree-sitter 0.27. The Svelte grammar does not.

## Why the Svelte grammar changed

svelte-ng 1.0.2 parses `{#if}…{:else}…{/if}` inside an element in **quadratic** time. The
grammar has not been maintained since 2024. A full parse of N copies of a 9-line `<section>`
block containing `{:else}`:

| N blocks | svelte-ng 1.0.2 | htmlx-svelte 0.1.16 |
|---|---|---|
| 200 | 0.50 s | 12 ms |
| 400 | 2.0 s | 24 ms |
| 800 | 10.9 s | 48 ms |
| 1600 | 39 s | 99 ms |

`tree-sitter-svelte-next` 0.1.1 (a svelte-ng derivative) behaves the same: 29.6 s at N=1600.

htmlx-svelte is MIT, maintained (last release 2026-06), covers Svelte 5, and is the grammar
Helix uses. It types expression content as `(ts)` or `(js)` from the component's
`<script lang>`, which handles "expressions follow the script language" in the grammar itself.

It depends on `tree-sitter = "^0.26"`, a normal dependency used only by a convenience function.
tree-sitter declares `links = "tree-sitter"`, so 0.26 and 0.27 cannot both be in the dependency
graph. That leaves three options:
1. tree-sitter 0.26 (chosen);
2. fork htmlx-svelte;
3. keep svelte-ng.

The 0.26 and 0.27 Rust APIs are the same for what quire uses. Move to 0.27 when htmlx-svelte does.

## tree-house 0.4 against our runner

| Question | tree-house 0.4.0 | Own runner |
|---|---|---|
| Builds with these grammars and tree-sitter 0.27/0.26? | Not as a drop-in. It does not use the `tree-sitter` crate: `tree-house-bindings` 0.3 vendors its own copy of the tree-sitter C library. Any grammar crate that depends on the `tree-sitter` crate (htmlx-svelte does) links a second copy of the same `ts_*` symbols into the binary. We saw the linker silently pick one copy when three Svelte crates each exported `tree_sitter_svelte`, so two different C runtimes would mix without any error | Uses the one `tree-sitter` crate the grammars use |
| Text input | `ropey::RopeSlice`. quire-core keeps ropey out of its public API (a hard rule), so we would have to expose the rope or copy the text per parse | Chunks from `Text::chunks()` |
| Injection correctness | Good (Helix) | Fixtures pass: `<script>`, `<script lang="ts">` (quoted, single-quoted, unquoted, with other attributes), `<style>`, `<style lang="scss">` skipped, every expression context, CSS in tagged templates, svelte > script > CSS template nesting (`tests/injections.rs`) |
| Incremental reparse | Calls `Tree::edit` on every moved layer (`parse.rs`, `flags.moved`). We measured that as the dominant cost on Svelte files with about 11k expression layers (below) | Lazy layer shifts plus shared layer data (below) |
| Licence | MPL-2.0 (a dependency is fine) | Ours |

The runner is about 1,000 lines: `tree.rs` and `highlight.rs`. Semantics:
- **Highlights:** when several patterns capture the same node, the last one wins (as in
  tree-sitter-highlight, nvim and Helix). An inner node wins over an outer one. An injection
  replaces its parent's styles inside its ranges.
- **Injections:** when several patterns inject into the same content node, the first one wins.
  `injection.combined` and `injection.include-children` are supported. Unknown languages claim
  the node and are skipped.
- **Indents:** `@indent` and `@outdent`, summed over the layers that contain the line.
- **Brackets:** `@open` and `@close` within one match (the convention of Zed's `brackets.scm`).

## Re-highlight cost (criterion, `crates/quire-syntax/benches/e5.rs`)

The fixture is a generated 20,000-line, 546 KB Svelte component (`tests/support/fixture_gen.rs`):
10% TS script, 80% markup with blocks and expressions, 10% style. It produces 11,082 layers. Each
measurement is a one-byte insert, then an incremental parse of all layers from the previous tree,
then highlighting 60 lines around the edit.

| Edit | Reparse | Viewport highlight (60 lines) | **Total** |
|---|---|---|---|
| Markup expression | 7.3 ms | 0.77 ms | **7.8 ms** |
| Markup text | 7.1 ms | 0.75 ms | **7.6 ms** |
| Script | 4.2 ms | 0.38 ms | **4.8 ms** |
| tree-sitter root reparse alone (the floor) | 3.7 ms | | |

**The ≤ 2 ms target is not met, and no engine on tree-sitter can meet it here.** tree-sitter's
own incremental reparse of the 546 KB root tree after a one-byte edit takes 3.7 ms, whatever the
edit position. The same size of plain TypeScript takes 7.6 ms. For the markup cases, the rest of
the time is:
- `Tree::changed_ranges` on the root, about 1.6 ms (needed to find injections whose structure
  changed far from the edit);
- layer bookkeeping and the drop of the old tree, about 1 ms.

The work is off-thread. The driver shifts the previous tokens on every edit, so nothing flickers
while a job runs. A 20k-line component gets fresh tokens about 8 ms after the debounce.

Recommendation: change E5's target to "≤ 2 ms + tree-sitter's root reparse" or "≤ 10 ms
off-thread for 20k lines". Alternatively, measure the target on files under about 5k lines, where
the whole edit costs under 2 ms because the root reparse scales with file size.

How the engine got here, measured on the same fixture and edit:

| Step | Reparse |
|---|---|
| Naive: injection query over every layer, `Tree::edit` on every layer | 290 ms |
| Injection query only over changed ranges | 27 ms |
| Lazy shifts: layers after the edit's last line move without `Tree::edit` | 12 ms |
| Script and style injection patterns rooted at `start_tag` instead of `element` (2.6 ms → 47 µs per range query: element-rooted patterns made the cursor descend into every sibling element before the range) | 9 ms |
| Carried layers share their data through `Arc` (no tree copy or free per layer) | 6.5 ms |
| Whole-line threshold computed once per edit, not by a rope line lookup per layer | 6.8 → 7.3 ms in criterion, which also counts dropping the old tree |

Full parse (first open): about 0.6 s for all 11k layers. Full highlight of all 20k lines: 0.2 s.

## Correctness checks

- `tests/incremental.rs` applies random streams of one to three edits per change set: brackets,
  quotes, comments, blocks, `lang="ts"` and non-ASCII text. After every step, the incremental
  result must equal a parse from scratch in highlights for every line, folds, brackets and the
  injection list. With `QUIRE_FUZZ_SEEDS=40`, 7,900 steps were compared.
  - Steps where tree-sitter itself builds a different tree incrementally (error recovery; some
    layer's S-expression differs) are counted and skipped. That was 16 of 1,561 Svelte steps,
    and the count is the same with lazy shifts turned off, so the difference is not ours.
- Bugs these tests found and that are fixed:
  - `changed_ranges` was called new → old;
  - overlap with the changed ranges was inclusive in one place and strict in another;
  - unknown-language claims did not evict old layers;
  - combined injections were only partly re-found.
