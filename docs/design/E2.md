# E2: rope benches (quire-core)

`scripts/cargo.sh bench -p quire-core --bench e2` (`crates/quire-core/benches/e2.rs`). One run,
2026-10-22, on branch `core2` at `987ac37` plus the bench. Machine: macOS, Intel i7-8750H @ 2.20 GHz,
32 GB, rustc 1.98.0, release profile (criterion 0.7, 30 samples, 3 s). The machine is shared
through `scripts/cargo.sh` build slots, and other lanes may have been building during the run, so
treat the numbers as an upper bound rather than a baseline.

Corpus: generated source-like text, lines of 20–100 bytes (about 45 bytes average), indented with
spaces.

## Memory against file size

Process RSS delta around `Document::new` after dropping the contents string. This covers the
rope, the token store (one empty line entry per line) and the saved-text snapshot (shared, so not
a copy).

| File | Lines | Load | RSS delta | × text |
|---|---|---|---|---|
| 1 MB | 22 079 | 8.3 ms | 1.6 MB | 1.60 |
| 10 MB | 220 685 | 84 ms | 13.7 MB | 1.37 |
| 100 MB | 2 205 999 | 866 ms | 138 MB | 1.38 |

Load is linear, at about 115 MB/s (line-ending detection plus the rope build). A 100 MB file is
past the large-file thresholds (20 MB, 300k lines), so the document reports `Degraded` and syntax
features stay off.

## Edit latency at 100 MB

`Document::apply` with a one-character insert at a random position. Each edit is its own undo
group (2 s apart), so the cost includes history recording, the token shift, recent-changes
bookkeeping and the diagnostics map. There are 10 000 edits.

| p50 | p90 | p99 | max |
|---|---|---|---|
| 13.1 µs | 14.4 µs | 19.6 µs | 134 µs |

criterion `e2_edit/apply_insert_100mb`: 11.3 µs mean (CI 10.9–11.5 µs). That is far below a
frame (16 ms), and the target in ARCH-QUIRE §3.9 is met with large headroom.

## Line fetch

| Bench | 1 MB | 100 MB |
|---|---|---|
| `line(i).to_string()`, random line | 1.21 µs | 1.70 µs |
| 50 consecutive lines through `line(i).chunks()` (one viewport) | 41.5 µs | 45.8 µs |

Line access is O(log n) and nearly flat from 1 MB to 100 MB. A viewport of 50 lines costs about
46 µs, which is under 0.3 % of a frame. `line()` does two rope lookups per line (start and end), so
a per-viewport iterator could halve this if the widget ever needs it.

## After TC0 (two-backend `Text`)

One run on 2026-10-22, branch `tc0` at `1eb8ead`. It ran in a quiet window (the coordinator held
the other lanes), with the clock capped (CPU_Speed_Limit 46) and load averages of 4.9 / 6.6 / 12.0.
Files above 64 KiB stay on ropey, so this checks that the large-file path is unchanged.

| Measure | QE2 | After TC0 |
|---|---|---|
| Load, 1 / 10 / 100 MB | 8.3 / 84 / 866 ms | 4.9 / 48 / 487 ms |
| Edit at 100 MB, p50 / p90 / p99 | 13.1 / 14.4 / 19.6 µs | 9.4 / 10.4 / 14.5 µs |
| criterion `apply_insert_100mb` | 11.3 µs | 8.0 µs |
| `line_to_string`, 1 MB / 100 MB | 1.21 / 1.70 µs | 1.24 / 1.75 µs |
| 50 visible lines, 1 MB / 100 MB | 41.5 / 45.8 µs | 43.2 / 47.5 µs |

Line fetch is within noise. Edits and loads are faster, because `apply` edits in place and
change sets are stored inline. The RSS deltas this run (1.7 / 4.8 / 36.3 MB) are below QE2's
because of how the process RSS was sampled, not because the rope got smaller, so they are not
compared.
